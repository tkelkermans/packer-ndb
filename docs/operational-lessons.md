# Operational Lessons

Behaviour of NDB, Nutanix AHV, cloud-init and the guest operating systems that
is not obvious from their documentation, and that this project has hit in
practice. Read this before changing anything related to NDB provisioning, PAM
and SSH on Debian-family clones, storage and device-mapper handling, or image
capture — several of these took a long time to diagnose and are easy to
reintroduce.

Each entry is written as guidance, not history: if you learn something the hard
way, add it here in the same style.

- Do not treat a manually remediated live VM as proof that the saved image is correct. If NDB profile creation only succeeds after live package installs, rebuild the image from the project code and recreate the profile from that rebuilt image.
- PostgreSQL software profile creation in NDB checks HA support binaries even when the first provisioned database is a single instance. Matrix `ha_components` must be passed into Ansible, installed, validated, shown in the wizard, and reflected in the image name.
- Post-build artifact validation must receive the same matrix-derived validation inputs as build-time validation. If a new matrix field affects in-guest validation, pass it to `scripts/artifact_validate.sh` and add a self-test that captures the generated artifact-validation vars.
- Avoid parallel `op run --env-file=.env` calls when `.env` is provided by 1Password as a mounted/managed file. Serialize live commands that read secrets to avoid intermittent parse or read failures.
- Do not inspect `.env` with `cat`, `sed`, or similar commands. In this project `.env` can be a 1Password FIFO, so direct reads block and can consume the mount stream. Use one serialized `op run --env-file=.env -- ...` command at a time and first verify a harmless variable is present.
- If NDB provisioning fails at `Create and Attach Data Storage` with `Failed to apply VM Best Practices`, pull the NDB operation diagnostic bundle before classifying root cause. In this project, the top-level error looked storage-related, but the driver log proved the cloned VM already had PostgreSQL bound to port `5432`.
- PostgreSQL software profile images must not boot with the packaged PostgreSQL service listening on `5432`. NDB needs PostgreSQL packages/binaries in the image, but it must own the runtime database process during provisioning; validate service inactive/disabled and port-free before image capture.
- A temporary source VM may need PostgreSQL running so NDB can register it and create a software profile, but the unit must remain disabled. Verify the provisioned clone, not only the source VM: the clone should start with packaged PostgreSQL inactive/disabled until NDB starts its managed database runtime.
- OpenSSH drop-in ordering matters. Cloud-init can write `50-cloud-init.conf`; project overrides that must win should use an earlier or otherwise deterministic ordering based on the target SSH setting semantics.
- Keep NDB database names short during automated smoke tests. NDB rejected a generated PostgreSQL database name longer than 28 characters.
- Before calling an NDB software profile HA-ready, verify the full lineage: profile `SOURCE_DBSERVER_ID`, NDB DB server VM UUID, Prism VM boot disk `data_source_reference`, and Prism image name/UUID. A profile description or image-name convention alone is not enough.
- NDB API create/register/provision responses can say `status=success` before the async operation succeeds. Always wait the returned `operationId` and classify terminal operation status, not only the initial API response.
- The NDB server env vars are `NDB_SERVER_ADDRESS`, `NDB_SERVER_USER`, and `NDB_SERVER_PASSWORD`. Do not probe legacy guesses such as `NDB_SERVER` or `NDB_SERVER_USERNAME` when validating the 1Password-loaded environment.
- MongoDB DB server registration must point `software_home` at a software root, not a binary directory. `/usr/bin` fails version discovery, but `/usr` is also unsafe because NDB records that path as the software disk mount point and can overmount `/usr` during provisioning. Use a dedicated root such as `/opt/ndb/mongodb` with the required MongoDB binaries available under `bin/`.
- MongoDB software profiles require MongoDB Database Tools under the selected software home. At minimum, validate `mongodump` and `mongorestore` in `/opt/ndb/mongodb/bin`; NDB profile creation fails during `Process database server VM` if these are missing.
- For NDB operation failures, inspect failed step messages before acting on the top-level message. MongoDB profile creation appended a generic SELinux warning, but the failed step identified the real missing `mongodump` root cause.
- NDB 2.10 MongoDB provisioning on Red Hat-family guests is not safe with SELinux enforcing unless a complete custom policy exists for NDB's MongoDB paths. The NDB register-host logs state `Application type is mongodb_database. SELinux context setup not implemented yet, skipping`; direct `mongod` startup can pass while the service-managed provisioned database later fails with `ECONNREFUSED`.
- NDB network profiles are engine-specific. A PostgreSQL network profile cannot provision MongoDB; discover or configure a READY `mongodb_database` network profile before MongoDB E2E.
- Do a Prism image preflight before full E2E provisioning. Manifest success is not proof that the saved image still exists in Prism.
- Project helper scripts are Bash scripts. When sourcing `scripts/prism.sh` or similar helpers manually, run them under `bash`, not `zsh`, because Bash-specific indirect expansion such as `${!var_name}` is used.
- Do not rely on pre-seeded `/etc/rc.local` content for NDB target clones. NDB overwrites `/etc/rc.local` during create-DB-server disk preparation, then appends its static-IP script before its password-reset script. Hooks that must run before target networking should attach to `networking.service` or another file NDB does not rewrite.
- Do not order Debian `ssh.service` directly after `rc-local.service` in these images. Artifact validation and source-image probes use cloud-init `runcmd` to start SSH; making SSH wait on rc-local can deadlock normal first boot when cloud-final is still running and rc-local is still pending.
- On Debian-family NDB target clones, an early SSH attempt can pass password authentication but fail PAM account management before `rc-local` completes the injected reset. Treat `Access denied for user era by PAM account configuration` as an account-phase problem and hook normalization before `common-account`, not only before `common-auth`.
- When building passive target probes, quote remote SSH payloads with a script file or stdin form. A malformed inline `bash -lc { ... }` payload can hide the most important evidence, such as `/opt/era_base/era_startup.log`.
- Do not let PAM/account fallback logic unblock the Debian SSH reset gate merely because `/bin/reset_password.sh` is absent. During NDB target boot, `/etc/rc.local` can already reference a pending reset while the script path is transient; only the reset completion marker should unblock the gate from PAM paths.
- NDB can attempt SSH to a newly created Debian target before it has finished writing `/bin/reset_password.sh` or appending the reset hook to `/etc/rc.local`. Do not solve that by blocking normal `ssh.service` startup: artifact validation and source VMs depend on cloud-init/key-based SSH. Handle the early NDB password attempt in the PAM auth path and skip the wait on normal cloud-init boots.
- When inspecting NDB state or payload JSON, never print raw `actionArguments` values. Some fields that look like ordinary provisioning inputs contain generated database or OS passwords; select names only or redact values whose names include `password`, `secret`, `key`, or `token`.
- Live NDB API calls can legitimately take longer than a small curl default in a VPN-backed lab. E2E runner request timeouts must be configurable and documented; classify an empty curl timeout separately from image/provisioning failures, then check whether NDB created the requested entity before retrying.
- Do not use cloud-init user-data presence to distinguish normal source boots from NDB target clones. NDB clones can retain source cloud-init metadata. For Debian target password-reset timing, the more useful early signal is that NDB has created `/etc/rc.local` while `/bin/reset_password.sh` is not visible yet; normal E2E source VMs do not have that file.
- Avoid long PAM waits in NDB target authentication. They can keep NDB stuck inside `Create Virtual Machine` before it reaches later reset-script injection. If NDB is already attempting password auth and PAM exposes the attempted token, setting the drive-user password from that token is safer than waiting for a future reset script.
- On Debian-family target clones, `pam_nologin` can reject the NDB drive user while `/run/nologin` is still present even after the password has been corrected and the account is unlocked. If early SSH must be allowed for NDB, bypass only `pam_nologin` for the configured drive user and still run the normal account stack.
- NDB operation diagnostic bundle download IDs are not always the original operation IDs. Use the bundle creation response `workId` or `id` when downloading the generated archive.
- If a failed child operation reports `No debug information could be retrieved` and rollback cannot copy the child target bundle from `/opt/era_base/tempdir`, do not claim target diagnostics are complete. The target runner may have failed before packaging its own child-operation bundle.
- Apparent NDB clock skew warnings can be timezone-formatting noise. Confirm NDB server `timedatectl` and chrony state, and verify the warning's DB server or operation ID, before treating skew as a provisioning root cause.
- NDB release-note tables can qualify exact database patch ranges while this project's matrix rows express only major versions. For E2E failures on a supported major, compare the installed patch from profile or target metadata against the release-note patch range before blaming OS boot, SSH, or image layout.
- PGDG archive package indexes may publish historical PostgreSQL server packages while `postgresql-contrib-<major>` is only a virtual capability provided by the server package. Do not require a separately versioned contrib package for pinned Debian/Ubuntu builds unless `apt-cache madison` proves it exists.
- If a release-note-qualified PostgreSQL patch rebuild still fails at the same NDB `Registering Database` step, stop treating package drift as the root cause. The next evidence must come from transient target-side register runner logs or NDB driver diagnostics, not more package pin changes.
- For rollback-prone NDB target failures, capture transient target evidence from inside the same serialized E2E process. A separate parallel `op run` can contend for the 1Password-backed environment and may miss the short target-VM window.
- Target observer process snapshots can expose secrets in command-line arguments, especially Ansible extra vars. Redact known password arguments and avoid tailing non-log register payload files before sharing observer output.
- If Debian/Ubuntu NDB registration fails with `Failed to get storage mappings` and `/dev/dm-N..` lookups, a disposable source-VM workaround is not enough. NDB creates the final target VM itself, so device-mapper alias and udev serial compatibility must be baked into the image and rerun after NDB attaches its Era LVM volumes.
- Timer-based device scanners must ignore aliases they create. The Debian/Ubuntu NDB Era device-mapper helper must process only real kernel device names like `dm-0`; otherwise `/dev/dm-0..` matches the next glob and the timer recursively creates `/dev/dm-0....`.
- On Debian/Ubuntu PostgreSQL pinned builds, pin the matching `postgresql-client-<major>` package as well as `postgresql-<major>`. NDB uses `pg_config` from the client package for software profile/version detection, so a pinned server with a newer client still looks like the newer, unqualified PostgreSQL patch level to NDB.
- NDB's Linux precheck script is not the complete runtime requirement list. The PostgreSQL registration driver calls tools such as `parted` during storage mapping, so image validation must cover observed NDB driver commands as well as the precheck script output.
- E2E source VMs cloned from already-built images should use offline-safe cloud-init. Do not reuse Packer source-image bootstrap user-data for E2E provisioning runs, because package updates can block on DNS or repository availability before NDB validation begins.
- Debian/Ubuntu `/dev/dm-N..` compatibility must not create real block-device nodes. Real block aliases can pollute NDB storage metadata and make the NDB Era agent VG appear as `OS_SOFTWARE`; use symlink aliases to satisfy malformed path lookups without adding another block device candidate.
- Do not assume symlink aliases are harmless in NDB storage mapping. NDB derives major/minor data from `ls -lh /dev/dm-N..`; a symlink can corrupt that lookup into unrelated devices like `/dev/urandom` and still leave the Era agent VG classified as `OS_SOFTWARE`.
- Do not use an omitted `timeMachineInfo` payload as a PostgreSQL pure-DB provisioning diagnostic. NDB `/databases/provision` creates the database together with Time Machine/protection metadata; omitting that section can fail dispatch before an operation ID exists.
- If NDB includes its own Era agent volume group in PostgreSQL DB server metadata and then sends that VG to Prism protection-domain `add_entities`, stop iterating image alias variants. At that point the remaining fix needs a supported NDB driver/product change or a documented NDB-side exclusion mechanism.
- A Debian-family systemd service ordered before `sysinit.target`/`basic.target` must not run a long watcher on normal boots. Use a fast early `oneshot` gate only; handle late NDB reset intent in networking, SSH, or PAM helpers, otherwise source clones can sit before D-Bus/SSH and E2E readiness appears hung.
- Artifact validation cloud-init can hide missing image-native boot services by installing or starting packages during validation. E2E source VMs use offline-safe cloud-init, so Debian/Ubuntu images must guarantee first-boot D-Bus readiness from the image itself and validation must assert the explicit systemd boot anchors.
- Saved-artifact validation must use offline-safe first-boot cloud-init by default. Once an image has been built, validation should not run package updates or installs, because repository work can hang in a slow lab and can mask whether the artifact itself is self-contained.
- Public source image URLs can move even when the qcow2 filename is still valid. Before trusting or changing an `images.json` direct URI, run an external HEAD check; `ImageCreate failed` with `Unable to fetch the file size from range request` and HTTP `404` is a source-image URL/import problem, not an Ansible or database-extension problem.
- Git commits on this machine are SSH-signed via 1Password (`op-ssh-sign`). A locked 1Password vault fails commits with `1Password: failed to fill whole buffer`. For unattended runs, fall back to `git commit --no-gpg-sign` on local branches and re-sign before pushing: `git rebase --exec 'git commit --amend --no-edit -S' <base>`.
- Run shellcheck per file (`xargs -n1 shellcheck`), not as one multi-file invocation: a single run cross-contaminates its variable-scope analysis across scripts and emits false SC2178/SC2128 ("used as array but assigned string" / "expanding array without index"). CI and the static-gate command both iterate per file for this reason.
- The selftest suite must run with stdin detached (`exec </dev/null`): sandboxed fake binaries that capture SSH payloads block forever when a background runner hands the suite a long-lived stdin socket instead of an EOF-ing terminal.
- Keep helper scripts portable to macOS `/bin/bash` 3.2: no `declare -A` associative arrays (use parallel indexed arrays), and guard empty-array expansions under `set -u` with the `${arr[@]+"${arr[@]}"}` form.
- A Packer `Timeout waiting for SSH` with a healthy, IP-bearing builder VM can be a local keypair mismatch, not a network or guest problem: if `packer/id_rsa` is ever regenerated without its `.pub`, cloud-init injects a public key the private key cannot answer and every auth attempt fails quietly until the timeout. Check `ssh-keygen -y -f packer/id_rsa` against `packer/id_rsa.pub` before blaming the VPN or the image; a direct `ssh -i` attempt surfaces the telltale `identity_sign: ... contents do not match public`.
- On Debian/Ubuntu, installing firewalld alongside cloud-init creates a systemd ordering cycle with no innocent victim: `firewalld` (which declares `Before=network-pre.target` but keeps default dependencies, so it is also `After=dbus.service` → `basic.target` → `sysinit.target`) closes a loop with Ubuntu's `cloud-init.service` (`Before=sysinit.target`, `After=networking.service` → `network-pre.target`). systemd breaks the loop by DELETING a job, alternating unpredictably between `cloud-init.service` (clone boots with no user and no SSH keys; `result.json` shows `getpwnam(): name not found: 'ubuntu'`, and only `init-local`/`modules:config`/`modules:final` stages run — the `init` Network Stage is missing) and `firewalld.service` (clone boots with its firewall down). The same image can boot correctly on a retry, so a single successful boot NEVER proves the cycle is gone.
- Do not try to cut that cycle with a systemd drop-in that resets `Before=`/`Wants=`: it did not remove the edge in practice (firewalld remained ordered before `network-pre.target` at runtime, and the loop simply changed victim). Shadow the vendor unit instead — generate `/etc/systemd/system/firewalld.service` from the installed unit with the `Before=`/`Wants=network-pre.target` lines stripped and `Before=ssh.service` added, so the guest is never SSH-reachable with its firewall down — and ASSERT the result during the build (`systemctl show firewalld --property=Before` must not mention `network-pre.target`). Verify on a booted clone with `journalctl -b | grep "Found ordering cycle"` (expect zero) plus the presence of cloud-init's `init` stage, not merely a successful SSH.
- `ansible.builtin.shell` runs under `/bin/sh` (dash on Debian family), which rejects `set -o pipefail`. Any pipefail-using task needs `args: executable: /bin/bash`.
